# 历史回测：设计与验证 v1.0

> 适用范围：`product/trade_master` 的回测功能（`app/backtest.py` / `app/backtest_data.py` /
> `app/backtest_calc.py` / `app/market_clock.py` / `engine/tradingagents/asof.py`）。
> 可执行回归：`python scripts/smoke_backtest_{data,match,isolation,calc}.py`、`node scripts/check_frontend.js`。
> 改动执行内核（`trust` / `trade` / `account` / `analysis_service`）后，还须一并跑非回测的
> `smoke_{ladder,snapshot_reset,chat_tools}.py` 与 `python -c "import app.main"`——回测复用的是同一套代码。

---

## 1. 为什么做

验证托管团队的能力，原本只有一条路：**从今天开始往后等**。三十个交易日才有一个勉强能看的
样本，而且样本量只有 1。回测要的是：取过去一段真实行情，在自选股范围内让这个团队**重跑一遍**，
逐日决策、模拟撮合，最后汇聚成成交流水 + 总盈亏 + 总资产 + 同期基准对比。

**这件事的成败只取决于一个问题：回测里团队看到的，是不是它当时真的能看到的东西。**
任何一处让模型读到"未来"的泄漏，都会让结果系统性虚高——而那恰恰是唯一要验的东西。
所以本功能的主线不是"再写一套回测代码"，而是**把未来函数堵干净**。

---

## 2. 两条设计主线

### 2.1 把"实时"表达成"历史的退化情形"

不写第二套执行代码。引入 5 元组 `Bar(open, high, low, close, prev_close, volume_ratio, tradable)`：

- **实时**（`LiveClock`）的 bar 是**退化 bar**：`open == high == low == close == 现价`
- **回测**（`HistoryClock`）的 bar 是真日线

于是梯子**选档**喂 `bar.low`（exit）/ `bar.high`（entry），**定价**用纯函数
`plan_actions.fill_price(action, bar)`。对退化 bar，这两者恒等于现价——与旧的标量路径**逐位相同**。
所以执行内核只有一份，`_pick_tier` / `_trigger_satisfied` 的口径不可能分裂。

> `clock is None ⟺ 实时` 是全仓库唯一的判别式（`trust.run_execution` / `trade.place_order` /
> `trade._check_limit` / `account.get_positions` / `analysis_service.*` 都按它分流）。

### 2.2 影子账户隔离

所有表都按 `user_id` 分区，所以给每个真实用户挂一个**稳定的影子 user**（`User.is_backtest=True`，
`phone = "bt-" + token_hex(6)`），账务全部落在它名下——`trust._execute_plan` / `account.get_positions` /
`trust.run_plan_for_user` 等既有代码**一行不改**就复用了。隔离由 `user_id` 天然完成。

**必须堵的实盘漏洞**：`trust._iter_active_users()` 会捞走所有 `is_active=True` 的 `TrustConfig`，
而 cron `_sched_execution` 在周一到周五 9:00–14:59 **每分钟**跑一次。影子账户一旦被选中，
调度器就会在真实盘中拿实时价交易回测账簿。两道卡口：

1. **选择侧** `_iter_active_users` 加 `.join(User).filter(User.is_backtest == False)`，并用
   `try/except` 包住（迁移未落地时退回旧查询，不能让调度器整体瘫痪）。
2. **激活侧** `toggle_trust` 对影子账户直接抛 `ServiceError`。

外加执行层的第三道：`run_execution` 里 `cfg.is_active` 是**实盘开关**，影子账户硬性为 `False`，
所以判据写成 `(clock is None and not cfg.is_active)`——回测走显式 `clock`，本身就等价于
"本次执行已被明确授权"。

> **正确性一律读 `User.is_backtest` 列，不解析手机号前缀。** 前缀只是给人看的。

### 2.3 镜像：冻结值必须真的落到影子上（2026-09-11 修）

**这一节记录的是一次静默失效**——回测能跑完、不报错、结果页看起来"团队很保守"，
实际全程零成交。追下来，回测一天的三截管道**只有第一截读的是冻结值**：

| 环节 | 读的是谁 | 断链时的现状 |
|---|---|---|
| 取数 / 数据门禁 / 收益聚合 | 冻结的 `universe_json` | ✅ 对的 |
| **Stage1 研究** | 影子的 `get_analysis_universe(sh)` | ❌ 影子池是空的 → `EngineRun` 恒为 0 |
| **Stage2 决策上下文** | 影子的**持仓** | ❌ 候选池进不到团队眼前 |
| 执行（下单/费用/风控） | 影子的 `TrustConfig` | ❌ 全是 db 默认值，用户设的费率/风控不生效 |

根因只有一句：**发起时的冻结值（`config_json` / `universe_json`）从来没有被写到影子账户上。**
`_ensure_shadow_config` 建的是**默认** `TrustConfig`（`stock_scope=0`、费率风控全默认），
影子自选表是空的。于是空仓起步 → 研究 0 条 → 团队一个代码都看不到 → 产不出计划 →
执行层返回 `no_plan_backtest` → **零成交、零费用、总资产恒定**。所有研究经费都花了，
报告落进 `EngineRun`，然后没有任何环节读它。

> **`_validate_startable` 本想拦住"空仓起步 + 空池"**，但它读的是 `config_json["stock_scope"]`
> （**发起人**的托管 scope），而执行层读的是**影子**的 scope。**校验读的键与执行读的键不是同一个**——
> 这是本缺陷最精炼的表述，也是"为什么它不报错"的答案：校验自己觉得自己是对的。

**修法（`app/backtest.py`）**：两处启动路径（`apply_initial_state` 全新起跑 / `_restore_checkpoint` 续跑）
都调 `_apply_frozen_config` + `_materialize_universe`：

- `_apply_frozen_config(cfg, frozen)`：写入 `_SETTING_FIELDS` 中除 `stock_scope` /
  `stock_scope_group` / `agent_id` 外的全部键（`style`、三个风控、三个费率）。
  **绝不碰 `available_cash` / `book_created` / `broker_*`**——字段集与 `_SETTING_FIELDS` 不相交，
  将来若往里加金额型字段，会覆盖检查点恢复的现金。
- **`stock_scope` 必须跳过而不是照抄**：抄到 0，执行层的 `empty_start` 不成立，空仓起步照样零成交；
  抄到 2 语义含混。改为**强制 `stock_scope=1`、`stock_scope_group=None`**，让执行层取"影子全部自选"。
- `_materialize_universe(...)`：先删影子全部 `Watchlist` / `WatchlistGroup` / `WatchlistMeta`，
  再写入**一个**分组（常量 `BACKTEST_GROUP = "回测标的池"`）与冻结池的每一只票。**幂等**。
- `_restore_checkpoint` 里**顺序是硬约束**：镜像 → 物化 → `book_created = True` → 写
  `available_cash`。现金必须最后写，否则会被镜像或物化路径上的新建默认值盖掉。
- **续跑也要重新物化**：同一发起人的所有 run 共用一个影子账户，而 `_ACTIVE_RUNS` 是按 run
  而不是按 owner 加锁的——并发两个 run、或删掉一个 run，都会踩坏另一个的池。幂等重物化 = 自愈。

于是四处自动对齐，**`trust.py` / `trade.py` 一行都不用改**（这是本方案最大的省力点）：

- `get_managed_symbols(sh)` = 冻结池
- `get_analysis_universe(sh)` = 影子持仓 ∪ 冻结池 = 冻结池
- `run_execution` 的 `empty_start` 对空仓起步恒成立
- 取股票名的 `names` 不再取空（另外把 `code→name` 冻进 `bt_names`，不依赖影子池里的名字）

同时 `_validate_startable` 改成读**执行层真正读的那份数据**（`universe_json` 是否为空）。
**行为变化**：`cash` +「持仓股」范围从"被拒"变为"合法"。

### 2.4 Stage2 必须看得见候选池（**同一处也修了实盘**）

`build_portfolio_plan_context` 全仓只有**一个**调用方，被**实盘计划生成与回测共用**。
它原先只把**持仓**的研究摘要塞进 Stage2 上下文——于是：

**实盘里选「自选股」几乎不生效。** `get_managed_symbols`（唯一读自选池的函数）只有三个调用点：
Stage1 研究、兜底建仓、对话助手只读展示。而兜底建仓那条被 `empty_start` 把关。所以：

| 当天情况 | 走哪条路 | 自选股在里面吗 |
|---|---|---|
| **有计划**（常态） | 执行计划里的 code | ❌ 团队看不到自选股，产不出它们的动作 |
| 有持仓、没计划 | 评级兜底 | ❌ `empty_start` 为 False，只对持仓评级加减仓 |
| 空仓、没计划 | 评级兜底 + `empty_start` | ✅ **唯一生效的场合** |

即：**只要托管簿里有持仓，选「自选股」对真实交易基本不起作用**——Stage1 花钱把自选股研究了一遍，
报告落进 `EngineRun`，然后没有任何环节把它交给决策团队。而设置页确实保存并显示了「自选股」，
界面上看不出异常。**这跟回测那个洞是同一个洞，只是在花真钱。**

修法：标的集从"持仓"扩到 `trust.get_analysis_universe(user_id)`（= 持仓 ∪ 在管池），
研究摘要分**【持仓】/【候选】**两组输出，并在文案里给出约束
「本次的建仓与调仓应限定在上面列出的标的范围内」。**不需要新增参数**——影子池已在 §2.3
被物化成冻结池，所以实盘自动读真实在管池、回测自动读冻结池，同一段代码两边都对。

> ⚠️ **这条约束是提示词约束，不是代码硬保证。** 用户明确选择不加越界硬约束。
> 回测侧有天然保护（`_drive` 只为冻结池取行情，范围外的票在 `clock.bars()` 里没有 bar →
> `tradable=False` → 执行层跳过），**但那是"没有行情"，不是"被拦下"**。

**实盘的止血手段（无需发版）**：把托管设置的选股范围改回**「仅持仓股」**，
`get_managed_symbols` 就只返回持仓，【候选】段自然为空，行为立刻回到改动前的样子。
**选股范围就是这次改动的开关。**

### 2.5 计划层空转必须判成失败日（2026-09-12 修）

**又是一次静默失效，而且和 §2.3 是同一个形状**：回测跑得完、不报错、结果页看起来"团队很保守"，
实际全程零成交。区别只在断点位置——§2.3 断在"影子池是空的"，这次断在**计划层的返回值被丢掉**。

`analysis_service.run_portfolio_plan_for_user` 拿不到可用方案时 `return None`、**不抛异常**
（该函数里有两处 `return None`，判的都是 `actions` 为空，见本节末）。而 `_drive` 此前是这么调的：

```python
run_analysis_service.run_portfolio_plan_for_user(sh, days[i + 1], clock=clock, research_date=d)
```

返回值没接。于是：`TrustPlan` 不落库 → 次日执行层没有计划可依 → 又一天零成交 → 而 `step`
照样被标成 `ok`，五天后 `_finalize` 照样写一个看起来正常的 `result`。**实盘入口对同一情形
本来就是 `raise ServiceError("组合决策层未产出有效行动方案，请稍后重试")` 的**——所以这个洞
只在回测侧存在，只在回测侧静默。

> **为什么这条比 §2.3 更要紧**：`_MAX_CONSECUTIVE_ERRORS` 的注释写着，回测**唯一**要验的东西
> 就是"团队有没有在市场里真的动过手"。一个连续几天什么都没做、却报告 `done` 的回测，
> 恰恰是回测最该报错的那种结果。**静默在这里不是少一个功能，是给出一个反向的结论。**

**根因不是机制坏了，是失败被吞。** DeepSeek 全系是 thinking 模型、拒 `tool_choice`
（见 `llm_clients/capabilities.py` 的 `_DEEPSEEK_THINKING`），schema 只能当**工具**发出去、
模型**可以不调**，于是偶发地纯文本作答、解析器拿到 `None`。实测这与**并发/限流强相关**：
回测里 23 路研究并行时必现，单发同一段上下文 8/8 成功。逐个证伪的假设：机制断了（否，
`function_calling` 4/4 OK）、`json_mode` 能修（否，4/4 HTTP 400 `Prompt must contain the word 'json'`）、
上下文超长（否，真实上下文仅 4330 / 11557 字符）、`max_tokens` 截断（未复现）。

**两处修法：**

1. **`_drive` 必须看返回值**（`app/backtest.py`）：空计划 = **失败日**，`raise ServiceError`，
   由既有的 `except` 标 `degraded`、`consecutive_errors += 1`，连错
   `_MAX_CONSECUTIVE_ERRORS`（=3）天中止整轮。**不新增失败通道**——复用"单日偶发失败只记
   degraded、连错才中止"这条既有口径，所以一次 LLM 抖动不会废掉十小时的长跑。
2. **`invoke_structured` 失败重试一次**（`engine/.../utils/structured.py`）：只重试**一次**。
   实测隔一次再问通常就拿到工具调用了；再失败说明是系统性问题（配额耗尽 / 鉴权 /
   模型确实不调工具），继续重试只是把同一个错误写得更慢，应当让调用方看见并据此判定失败日。
   `invoke_structured_or_freetext` 那条路径**不受影响**——它本来就有自由文本兜底。

**判定"空计划"的口径**：`if not plan or not plan.get("actions")`。`PortfolioPlan.actions`
**没有 `min_length`**，所以空列表在 schema 层合法——`plan == {}`（结构化失败）与
"有 dict 但 actions 为空"（团队真的决定按兵不动）在 schema 层可分。

但**这条区分到不了回测这层**：`run_portfolio_plan_for_user` 的**两个 `return None` 都判的是
`actions` 为空**（一次在归一前、一次在 `sanitize_ladder_actions` 之后），所以它返回的方案
**必有非空 `actions`**。回测侧的 `not plan.get("actions")` 分支因此是**防御性**的、
当前不可达——保留它是为了让"计划层将来改成返回空方案"时不至于重新静默。

> ⚠️ **由此有一处口径要说清**：若某天的动作**全部被 `sanitize_ladder_actions` 剔掉**
> （档位非法/方向冲突），函数返回 `None` → 回测按**失败日**处理。这是对的——动作一个都不
> 合法的计划确实不可执行；但它与"团队决定按兵不动"在函数出口处**长得一样**，
> 要区分就得改 `analysis_service` 的返回契约，本轮不改（实盘入口对两者也是同一条 `raise`）。

**回归断言**：`scripts/smoke_backtest_calc.py` 第 10 节的「丁」段，两种坏返回值各 8 条：
`None`（真实会发生的那个）与空 `actions`（走的是上面那条**防御性**分支，为将来留的门）。
其中两条专门钉住"中止是**真的**停住"：中止后第 4、5 天**连执行层都没进**（不是标个失败
继续跑满），且抛之前先存了检查点，所以**实库与检查点一致**（对比第 10 节乙段：那里是
进程被杀、没机会存，两者必须**不一致**）。另有一条反例由同节甲段守着：计划层给得出方案 ⇒
全 5 天 `ok`、状态 `done`、固定声明一条不少——**新加的判据不能把正常路径也判成失败**。

### 2.6 计划不是"运行痕迹"：影子账户的重置不许删计划（2026-09-12 修）

**现象**是用户报的「9.7-9.8 的报告去哪了」——报告页凭空少了那一天。**根因不在报告页**，
而在影子账户的重置：`backtest.reset_shadow_book` 复用了 `trust._clear_book_runtime`，而后者
的 docstring 明写它清的是「委托 / 成交 / **次日行动计划** / 已实现盈亏」。于是**后一次回测
一开跑，前一次回测的计划行就没了**。

两天的性质完全不同，必须分开说：

- **09-07 是设计**。计划「研究日日终产出、次日执行」，回测首日没有前置研究日，所以这天
  **永远不会有**报告。它不是丢了，是从未存在。
- **09-08 是被删的**。证据链（都是库里的既有事实，不是推断）：
  - `trust_plans` 的 id 从 5 跳到 8 —— 中间 6/7 被消耗而无行，正是重置那个窗口；
  - run 1 的 step `2026-09-08` 是 `plan_json` 里 `actions` 为空、而 `status='ok'`；
  - 而 `EngineRun` 里 09-07、09-08 各有 23 份研究报告**都还在**——研究在、计划没了。

**为什么影子路径删计划是必然后果，而不是疏忽**：影子账户被**刻意跨 run 复用**
（`ensure_shadow_user`：`EngineRun` 研究缓存是最贵的成本项，换新影子会让它全部作废）。
既然 run A 的计划本来就落在共享的影子上，那么"run B 的开始按运行痕迹清一遍"就必然抹掉
run A 唯一的历史记录。**计划是那次回测自己的产出，与"研究报告留着"是同一个立场。**

**修法：**

1. `_clear_book_runtime(session, user_id, *, plans: bool = True)` 加一个**显式关键字**。
   默认 **`True`** —— 真实账簿的「重置托管 / 重贴快照」**必须**清计划（清掉计划即同时清空
   监控卡片：监控条件不是独立表，而是 `TrustPlan` 的派生视图），这正是 docstring 里记着的
   那个老坑（清空逻辑曾在 `reset_trust` 里抄过一份并漏了 `TrustPlan`）。默认值反了会让它
   无声复活，所以**默认保持原语义**，只让影子路径显式地偏离。
2. `reset_shadow_book` 传 `plans=False`，并在 docstring 写清两条路径**为什么故意不同**。
3. `delete_run` **显式**删除本 run 窗口内的计划 —— 「删掉这次回测，它的报告就该一起消失」
   是这里该有的语义，且是 run 维度、可解释的删除，不再借道影子重置。

> **不走"每个 run 一个影子账户"这条路**：那会废掉刻意复用的 `EngineRun` 研究缓存
> （每次回测 ~10 小时的重算），代价远大于收益。跨 run 串味改由 §2.7 的**日期窗口收口**解决。

**代价要说清（做多轮验证时的排序约束）**：`plans=False` **只保住了计划，委托与成交两表仍然
会被后起的 run 清掉**——`_clear_book_runtime` 本就是"清空运行痕迹"。所以
**「`step.trades_json` 与 `trades` 表逐笔相等」这条验收判据只对影子账户上最新的那个 run 有效**：
要验就先把这一轮验完，再起下一轮。`scripts/verify_backtest_run.py` 的 A 条已按此加护栏
（检测到更晚的 run 就跳过该项并明确提示，而不是报一个假的失败）。

**实测影响不是"少一份报告"，是"吞掉一整天的执行"**：同一窗口 2026-09-07~09-11、同参数、
空仓起步，修前（run 1）09-08 无计划 ⇒ 那天零成交、整轮 1 笔；修后（run 2）09-08 有计划 ⇒
3 笔。所以"报告少一天"和"回测少一笔"是同一件事的两面。

**回归断言**：`scripts/smoke_backtest_isolation.py` 第 6 节——先给影子名下落一份计划，
再调 `reset_shadow_book`，断言「★ 影子账户的**计划留着**」且「委托/成交/持仓**照旧清干净**
（计划是唯一被豁免的那一样）」，同时真实用户的委托/成交/计划/持仓/自选股**分毫不动**。

### 2.7 报告清单以"跑过的交易日"为骨架 + 按 run 窗口收口（2026-09-12 修）

`list_plan_reports` 原先**只列有 `TrustPlan` 行的日期**，且只按 `shadow_user_id` 过滤。
两个毛病：① 缺计划的日子**直接从列表里消失**——用户看到的是"报告页少了两天"，而不是
"这两天没有报告"；② 影子共用时会把**别的 run 的日期**混进来。

**关键区分**：「没计划」和「有计划但一档都没触发」是**两回事**——前者说明团队那天根本不可能
做任何事，后者说明它做了判断但没动手。列表必须把前者**显式画出来**，否则报告页越完整越像是
在骗人。

**修法**：以 `BacktestStep`（= 这个 run 真实跑过的交易日）为骨架，左连接计划；每条给
`has_plan` 与 `plan_missing_reason`（`first_day` = 首日无前置研究日，属设计；`missing` =
非首日却真的没有计划行，是"环断了"）。计划查询按 run 的 `[start_date, end_date]` 收口。
`get_plan_report` 同样收口。前端 `btLoadReports` 据此把无计划的日子也列出来并标注原因，
而不是整块卡片退化成空态。

> ⚠️ **窗口收口解决的是「列出哪些日期」，解决不了「同一天互相覆盖」。** `TrustPlan` 的唯一键是
> `(user_id, trade_date)`，而影子账户**跨 run 复用** ⇒ **同一天的计划行后写覆盖先写**：
> run B 一旦写出它的 D 日计划，run A 的 D 日计划就没了（last write wins）。
> 这与 §2.6 的委托/成交擦除是**同一条排序约束的两个面**——前者擦计划，后者擦流水。
> 所以**重放或复核某一轮，必须在这一轮还是影子上最新的 run 时做**。将来若要让两轮并存，
> 得让计划行带上 `run_id`（唯一键变成三元组），那是另一个量级的改动，本轮不做。

**回归断言**：`scripts/smoke_backtest_report.py`（清单日期集合 == step 日期集合；
首日标 `first_day`、非首日缺计划标 `missing`，两者必须分得开）；前端
`scripts/check_frontend.js` 断言无计划日期会渲染成「首日无前置研究日 / 无计划」的选项，
且选中它时**不发请求、隐藏 iframe、禁用下载按钮**，改选有计划的日期后按钮恢复可用。

### 2.8 逐日成交与每日监控条件必须看得见（2026-09-12 加）

用户的两个诉求——「我要看到回测过程中的成交记录」和「每天的监控条件」——前者**后端早就有了**
（`GET /api/backtest/{run_id}/trades` → `backtest.get_trades`），**前端从未调用过它**，这就是
"看不到成交记录"的全部原因；后者确实缺，且缺得不只是接口。

**成交明细**：新增逐日成交卡片，**放在 `#bt-report` 卡片之外**。理由是 `#bt-report` 在没有
计划日期时整块隐藏，而成交与报告无关——放里面就会在"缺计划"这个正是本轮 bug 的场景下
一起消失。渲染上把三处（分析页 / 托管页 / 回测页）已经各写一遍的行渲染抽成 `tradeRowEl(t)`，
三处共用。回测里 `traded_at` 是**模拟时间**（`place_order(ts=…)`），所以直接复用现有时间
格式化即可，不会显示成回测跑的真实钟点。

**每日监控条件（执行口径）**：`trust.get_monitor_conditions` 原先**没有注入缝**——硬编码
`_get_latest_plan_row`（最新计划）+ `account.get_quotes`（实时快照），且在 `asof_scope` 内
`get_price_snapshots` 直接返回 `{}`，照搬会得到"每档价格 None、全不触发"的空卡片。

修法是加三个**默认 None = 今天行为逐字节不变**的注入参数（`plan_row` / `bars` / `now`），
新增 `backtest.get_day_monitor_conditions(run_id, owner, date)` 与
`GET /api/backtest/{run_id}/monitor?date=YYYY-MM-DD`。**触发判据本身仍走
`trust._trigger_satisfied` / `_pick_tier`，不另写一份**（`market_clock.py` 明令）。

> **口径是这一节的核心：卡片与撮合同一个判据——卖/减看当日最低、买/建看当日最高。**
> 用"回测跑到此刻的价"或"收盘价"来判，会出现**卡片说没触发、账上却成交了**的自相矛盾，
> 那这张卡片就失去了存在的理由（它存在的唯一理由就是解释当天的成交）。
> 于是逐档取价：`kind == "exit"` → `bar.low`；`"entry"` → `bar.high`；`"hold"` → `bar.close`，
> 并把开/高/低/收四个价一并回传，让卡片能把判据写在脸上。

**没有计划就如实说没有**：返回 `has_plan=false` + 原因词，且**一次网都不打**。返回一张
"价格全空、一档不触发"的假卡片，看起来像"团队看了但没动"，而事实是这天团队根本没有可执行的
东西。该日无计划时前端整块隐藏，不做假渲染。

**成本**：23 只票的缓存文件解析约百毫秒级，故加一个 `(run_id, date)` 的进程内 TTL 缓存
（60s），避免切换日期时反复重解析。

**回归断言**：`scripts/smoke_backtest_monitor.py`（22 项全绿）——用内存 SQLite + 临时候存目录
+ Wind 替身，专钉四件事：**执行口径**（卖档看 low、买档看 high，且用收盘价判会得出相反结论
的那一行就是判别力的来源）、**量比算不出时带 `volume_ratio_min` 的档必须不触发**（宁可不动
也不退化）、**无计划日 0 次网络调用**（替身是"一调用就炸"的那个）、**时间闸门走注入的模拟
时间而不是真实墙钟**。生产侧的端到端验证见
`scripts/verify_backtest_run.py` 的 F 条：当天成交过的标的，在当天卡片里必须找得到**已触发**档。

### 2.9 复制起始持仓必须换算进后复权口径（2026-09-12 修）

**症状**：run 4（C6，复制真实持仓起步）在**起跑次日**把一只沪深300ETF 全部清仓，
`卖 10400 股 → 14414.40 元`，而它在真实簿里的市值是 **51043 元**。回测因此凭空少掉
**36629 元（−71.8%）**，这笔钱当场变成现金，污染其后的每一天。

**根因**：§3.2 定了回测全程走后复权（`aftype=1`），而 `init_mode=copy` 把真实托管簿的
`cost_price`（**不复权**盘面价）原样搬进影子。于是同一个持仓行里 `cost` 与 `price` **不同口径**，
凡是"现价 vs 成本"的比较全部失去意义。实测该票复权因子 `f = 0.279`：

| 口径 | 该票 09-11 收盘 |
|---|---|
| 不复权（`aftype=2`，真实盘面 / 真实簿成本价的口径） | **4.9080** |
| 后复权（`aftype=1`，回测 bar） | **1.3690** |

比值恒为 `1/0.279 = 3.585`。止损判据 `bar.low < cost × (1 − pct)` 于是变成
`1.379 < 5.031 × 0.92` —— **恒为真**，任何一天都会触发。同一处失真还波及三处：

- `init_basis` 成了**混合口径**的数（430876.14，真实 464273.74），起始基准（分母）就错了；
- `calc.replay_realized` 拿 seed 的成本价当加权平均成本初值 ⇒ 该票已实现盈亏同样错；
- 该持仓的**权重被低估 3.585 倍**，直接影响 `risk_max_position_pct` 的判定与现金纪律的观察。

**修法**（`backtest._rescale_copied_book`，只在 `copy` 且**全新起跑**时调用一次）：
取起始日的 `f = 后复权收盘 / 不复权收盘`，把复制来的持仓换算成后复权空间的**等值**表示：

- **数量** `Q_h = Q_r / f` ⇒ `Q_h × P_h(d) == Q_r × P_r(d)`，**起始市值不变**。股数取整到
  整股，所以实盘上差**不足一股**的后复权价（实测 159300.SZ：51697.80 对 51698.40，约 1e-5）——
  这是"股票只能整股持有"的必然代价，不是换算误差；
- **成本** `C_h = f × C_r` ⇒ 浮亏比例与真实一致（`P_h/C_h == P_r/C_r`，**恒等式**，断言到 `1e-12`）。

于是止损判据化为 `f·low_r < f·C_r·(1−pct)`，**与不复权口径完全等价**；全清时的已实现盈亏
`Q_h·P_h − Q_h·C_h == Q_r·P_r − Q_r·C_r` 也逐分相等。换算后**紧接着**才调 `_basis` 算
`init_basis` 并落 `init_positions_json` —— 晚一步就会用一个混合口径的数当分母。

**真实数据实测**（2026-09-12，拿生产缓存里的真后复权 bar + 真取的不复权线跑一遍，
不是替身）：`159300.SZ` 起始日 09-07 后复权 **1.386**、不复权 **4.971** ⇒ `f = 0.278817`；
`10400 股 → 37300 股`、成本 `5.031 → 1.4027`；止损线的对照是本条最直接的证据 ——

| 日期 | 当日 low | 未换算（5.031×0.92=4.6285） | 换算后（1.4027×0.92=1.2905） |
|---|---|---|---|
| 09-07 | 1.3790 | **触发** | 不触发 |
| 09-08 | 1.3780 | **触发** | 不触发 |
| 09-09 | 1.3780 | **触发** | 不触发 |
| 09-10 | 1.3580 | **触发** | 不触发 |
| 09-11 | 1.3550 | **触发** | 不触发 |

**未换算那一列是 5/5 全触发** —— "恒为真"不是推断，是实测。

**三个刻意的取舍**：

1. **`|f−1| < 1e-3` 的票原样不动**（走 `warnings` 报出来，不静默）。真实事件量级 ≥1%，而 Wind
   只有 4 位小数、价格 ~1 元时相对量化误差 ≤~2e-4，`1e-3` 两边都不误伤。本例 6 只持仓里只有
   1 只有因子，另 5 只**逐字节不变**——"不需要换算的票不碰"比"统一换算再取整"更安全，
   后者会把 36600 股改写成 36596 股这种无意义的抖动。
2. **取不到不复权价 = 硬错误，绝不按 `f=1` 兜底**。f 错了与"没换"同级：一只 5 万的持仓会
   变成 1.4 万，而结果页上**完全看不出来**。所以在这里停下问人，与 §8.2 的 `unpriced`
   门禁同一个立场。
3. **股数变成"后复权等值股数"**（10400 → 37302）。这是 hfq 空间里唯一自洽的表示，但它
   **不是账户里真实的股数**——所以换算过的票逐只进 `warnings`，结果页必须声明。

**取数只走缓存**：不复权线由 `backtest_data.load_unadjusted_closes` 取（同一套 `pad_start`
与 as-of 封顶，只换 `aftype=2` 与缓存键的 `raw`），**它是为算复权因子而存在的第二条线，
不是第二个行情入口**。⚠️ 调用点必须**自己再开一次 `asof_scope`**：上文那个 `with` 块在
`load_benchmark` 就结束了，在作用域外 `_fetch_cached` **完全不碰缓存**（§3.4 的承重墙）——
而它**不会报错**，只是每一轮 copy 回测都重新打 Wind，让 §3.4 的预热与断网验收全部落空。
`scripts/warm_bars_cache.py` / `verify_bars_cache.py` 因此也多预热/多验收一条持仓的不复权线。

**实测影响面**：只影响 `copy` 起步的回测；**实盘不受影响** —— 实盘的报价与成本价同为不复权
（`_execute_legacy` 是 raw-vs-raw），口径本来就一致。

**回归断言**（`smoke_backtest_calc.py` 新增 19 项）：数量 ÷ f、起始市值不变、成本比例恒等式
精确到 `1e-12`、**止损判据在两种口径下等价**（且未换算的那版恒为真，证明这条断言有鉴别力）、
`f=1` 的票逐字节不变、被换算的票进 `warnings`、seed 原地更新、`init_basis` 回到真实值、
`1e-3` 阈值不误伤 4 位小数的量化噪声、窗口内因子变动被报出、缺不复权价时抛 `ServiceError`
且**不半途改掉一半持仓**、空仓起步**零次**不复权取数。

### 2.10 账户级失败必须立刻中止，并且说真话（2026-09-13 修）

**现象**：run 5 在 2026-09-12 22:45:57 中止，界面上的话是「连续 3 天无法生成计划，已中止回测」。
看到这句话的第一反应是管线出了 bug 或者网络断了 —— 于是查了一轮 Stage2、查了一轮并发，最后
才在 `docker logs -t` 里看到三行 **HTTP 402 `Insufficient Balance`**（打给 Portfolio Analyst /
Risk Officer / Portfolio Manager 三个节点，22:45:35 与 22:45:55）。**根因是 DeepSeek 余额耗尽，
不是接口中断**；而这句话一个字都没提余额。

**为什么会被伪装成"管线 bug"**：`invoke_structured` 的既有契约是「失败返回 `None` 让调用方回落」
（§2.5 的生成侧孪生）。对偶发的解析失败那是对的；对**账户级失败**（401 鉴权失效 / 402 余额耗尽）
它是错的 —— 那类失败**不是"这一次没拿到结构化结果"，而是"后面每一次调用都会失败"**。返回 None
于是触发了三段连锁：① 每个 agent 白跑一次 free-text 回落（也必然失败）；② `run_portfolio_plan_for_user`
的两个静默 `return None` 守卫把空计划交出去；③ `_drive` 按普通失败日累计，**照「连错 3 天」慢慢走完**
—— 多烧的那两天墙钟全是白烧的，而用户看到的是那句中性的、指向管线的话。

**改法**（`tradingagents/agents/utils/structured.py`，唯一判据来源）：

- 新增 `account_level_reason(exc)`：**只认死错，不认慢错** —— `status_code in {401, 402}` 或
  文本命中 `insufficient balance` / `invalid api key` / `authentication fails` / `no credit`。
  - **刻意不含 429（限流）**：限流是瞬时的，把它当致命会让一次抖动废掉几小时的回测进度 ——
    那正是这里要避免的反面。也**不含 403**：同一个 provider 上它常常只是某个端点的权限。
- 新增 `AccountLevelLLMError(RuntimeError)`，并且**打破 `invoke_structured` 的 None 契约向上抛**：
  在 `invoke_structured` 的重试循环里、以及 `invoke_structured_or_freetext` 的 `except` 里，
  先判账户级，是则**连一次都不重试**（重试必错），`raise AccountLevelLLMError` 取代回落。
- `backtest._drive` 的取计划 `try` 里，`except PlanCancelled: raise` 之后、
  `except Exception` 之前，插入 `except AccountLevelLLMError`：照**普通失败日的形状**收尾
  （step 标 `degraded` + 写明原因、当天执行结果照常入库、检查点停在最后一个完整日），
  但**不再等** —— 直接 `raise ServiceError`，`run.message` 里是真实原因与处置建议。

**效果**：同样是余额耗尽，中止时用户看到的是「LLM 账户不可用，已立即中止回测（不是连错三天判定）：
HTTP 402: Insufficient Balance。请充值或更换 API key 后从检查点续跑。」，且**少烧 2 天墙钟**。
实盘路径（`app/trust.py` 的取计划处）同样接住，译成「LLM 账户不可用（…）：请检查 API key
与账户余额」—— 与「这次没拿到结构化结果，请稍后重试」区分开，因为前者重试无用。

**残留（已知、记在这里）**：账户级失败的那一天照旧落一个 `degraded`，而**它后面那一天天然没有
计划**（计划是前一日日终产出的），所以即便 fail-fast，续跑仍会多出**恰好 1 个**无计划日
（原先是最多 3 个）。这是 §5 逐日时序的必然后果，不是缺陷。

**回归断言**（`smoke_backtest_calc.py` 新增 15 项，全量 987 + 195 = 1182 绿）：402/401 判为账户级、
**429/403/`ValueError("structured output returned no parsed result")` 明确不判**（有鉴别力）；
`invoke_structured` 遇 402 **只调 1 次**就抛（不是 2 次）；500 仍然重试两次后返回 None；
`invoke_structured_or_freetext` 遇 402 时 **plain 路径 0 次调用**；真实库上把
`run_portfolio_plan_for_user` 打桩成 402，断言 run 停在**第 1 天**（不是第 3 天）、
消息含「LLM 账户不可用」+`Insufficient Balance` 且**不含**「未产出有效行动方案」、
检查点现金与账面现金一致。

### 2.11 计划的**归属**：影子复用 + 窗口重叠时，新一轮会吃上一轮的计划（2026-09-13 记录，**修法待定**）

**现象**：C2（run 3）干净重跑后，验收的 E 条挂了 —— 断言"首日 `has_plan` 必须为 False"，
而 run 3 的 `2026-09-07` 显示 `has_plan=True`、19 条动作。那份计划不是它自己生成的：
run 3 的 `09-07` step 写于 `15:55:14`，而计划行 `id=20` 写于 `15:29:17`，**是 run 5 生成的**
（run 3 的日循环只生成 `days[i+1]` 的计划，永远不会生成 09-07 的）。

**根因是三处各自都对的实现叠出来的**：

1. `trust_plans` 只有 `(id, user_id, trade_date, plan_json, created_at)` —— **没有产生者标识**。
2. §2.6（P0-1）刻意让影子的计划**跨 run 保留**（否则 run 的报告会被别的 run 的生命周期抹掉）。
3. §2.6（P0-2）只把 `skipped == "no_plan_backtest"` 判成降级日；而 `trust.py:900` 是
   `if has_plan: return _execute_plan(...)`。

于是「库里那天有计划」就足以让新 run 的**首日豁免失效**，去执行一份**为另一个账簿生成**的计划
（run 5 是空仓起步逐步累计出来的账，run 3 是复制来的真实持仓），报告页也会把别人的计划算成自己的。
**只在"影子被多个 run 复用、且窗口重叠"时现形** —— run 5 的 `08-25` 前面没有别的轮次留计划，
所以它自己完全正常，正是这个原因让缺陷躲过了前两轮验收。

**为什么 §2.7 的"按 run 窗口收口"挡不住**：窗口能排掉窗口外的日期，排不掉**同一个日期上
由别的 run 写的那一行**。`09-07` 同时在 run 5 和 run 3 的窗口里。

**临时处置（本次）**：起跑前清掉影子在**本 run 窗口内**的计划行；**窗口外的不动**（那是别的 run
报告页的底稿）。实测有效：C2 的成交从污染那轮的 7 笔变成 13 笔，首日正确回到 `has_plan=False`。

**两条正式修法（待定）**：

- **A（小、对准）**：`start_run` 在**从零起跑**（检查点为空）时清掉窗户内计划。语义是
  "一轮回测拥有它自己的窗口"，与 TM-M12-27（"A 条只对影子最新的那个 run 有效"）同一立场。
  缺点：同窗口的两个 run 仍无法各自归属。
- **B（大、治本）**：给 `trust_plans` 加 `run_id`，写入带上、读取按 run 收口（实盘 `run_id` 为 NULL）。
  要迁移 + 改所有读写点，**会在实盘验收前动到实盘计划路径**。

**通用问句**：**「这条记录是谁产生的？读它的人知道吗？」** —— 只要一张表没有产生者标识、
又会被多个作业共享，就一定会有某一天被张冠李戴，而它的代价不是报错，是**让一整轮验证的结论悄悄失真**。

## 3. 未来函数的治理

### 3.1 两条日期注入通道

| 通道 | 用在哪 | 为什么 |
|---|---|---|
| 显式 `clock` 参数 | 执行层（要按档位拿 `high`/`low`/`open`） | 一个标量表达不了"同一根 bar 的三个价位" |
| `contextvars.ContextVar`（`asof.py` 的 `ASOF` / `asof_scope`） | 引擎数据层（模块级 `@tool`，拿不到对象图） | 无法穿参，只能靠上下文 |

**关键约束**：`analysis_service.run_plan` 用的是**裸** `ThreadPoolExecutor`，所以 as-of 必须
在 **worker 内部**设置（在 `run_analysis_cached` 里包住 `run_analysis`），在 `run_plan` 外面设会被丢掉。

### 3.2 复权：全程后复权

前复权（`aftype=0`）以"今天"为基准回溯重算，历史价随未来的分红送转变化 = **偷看未来**。
回测全程用 **`aftype=1`（后复权）**——复权因子只依赖 `t` 之前的除权事件，构造上无未来函数。

代价：绝对价位被每只票的常数缩放，**与当前盘面不一致**。因计划/触发价/成交价/盯市全走同一口径，
运行内部完全自洽，但必须在结果页声明。

**⚠️ 这条口径只管个股线。指数线（基准）做不到**——`index_data/get_index_kline` 根本没有
`aftype` 参数（`tools/list` 实测；个股那个才有）。指数是价格指数、本就无所谓复权，所以
沪深300 是分红除息后自然回落的，而策略那条线隐含分红再投资，**两者不是可比的总收益口径**。
处理方式是：基准只按**收益率归一化**后使用（起点都归到 `init_basis`），回答"这段行情本身
涨跌如何"，不做绝对价位对照。**主基准始终是等权买入持有**（§6），它与策略共用同一套手数
与费用模型，差异只剩"团队决策"本身——那才是"团队比躺着不动强吗"的答案。这一条同时写进
§11 与结果页声明。

**因此所有数据加载都必须包在 `with asof_scope(run["end_date"]):` 里**——包括 `trading_days`
与 `load_benchmark`。这里的目的**不是**对齐复权口径（指数没有），而是把 `end_date` 封顶到
as-of：漏一个，团队就会在回测里读到 as-of 之后的行情。

> **两次实测教训，同一个根因：参数契约照 docstring 猜，而不是照 `tools/list` 读。**
>
> 1. `get_index_ohlcv` 的 `period` 写成 `"1d"`、还传了个 `aftype`。真打接口服务端当场拒：
>    `Invalid value '1d' for field 'period'`。真实契约：`period` 是**数字口径的字符串**
>    （`'10'`=日K），且这个工具**没有 `aftype`**。
> 2. `get_wind_ohlcv` 把 `aftype` 发成了**整数 `1`**。服务端拒：`参数格式不正确:aftype`。
>    真实契约：`period` 与 `aftype` 的 `type` 都是 **`string`**（`count` / `top_k` 才是
>    `integer`）。实测 24 只标的**一只都取不到**，而离线冒烟 107 项全绿。
>
> 两次的共同点：**离线断言只检查"请求长什么样"，于是把错的口径、错的类型一并钉死了。**
> 所以 `smoke_backtest_data.py` 现在除了断言取值，还断言 `isinstance(..., str)`——
> 但**再多的替身断言也替代不了打一次真接口**（§10.1）。

### 3.3 数据工具降级

新闻、公告、三大报表、公司事件、宏观、风险指标、实时快照在回测中**不可用**
（这些接口只有自然语言问答、没有日期参数）。拦截点全部在
`engine/tradingagents/dataflows/wind.py`（唯一 vendor 实现），返回哨兵
`ASOF_UNAVAILABLE`，与仓库既有的 `NO_DATA_AVAILABLE` 风格一致，LLM 已学会把哨兵当"缺失而非信号"。

**结果是回测的信息完备度低于实盘，两者的绝对收益不可直接对比**；可对比的是同一套信息条件下
团队决策的相对高低。这一条写进了结果页声明。

### 3.4 取数缓存：只在 as-of 作用域内启用

回测动辄几十只票、每只一次 Wind 调用，而"同一区间反复跑"是试点阶段的常态（先 10 天、再 30 天、
改了起始资金再跑一遍）。`backtest_data._fetch_cached` 把 `(标的, 区间, 复权口径, 数据种类)`
的日线落盘到 `data/bars_cache/`（`data/` 已在 `.gitignore` 里）。

**承重墙是这一条：缓存只在 `current_asof()` 为真时才启用。** 没有 as-of 就**连读都不读**，
直接 `fetch()`——所以实时路径（前复权）的行为与加缓存之前**逐字节相同**。理由不是"省事"，
而是**实时价的历史会随未来的分红送转被重算**（§3.2）：缓存它等于拿一份"昨天算的历史价"
当今天的历史价，还带着漂移的复权基准。回测的后复权价在构造上不可变，缓存才是安全的。

| 设计点 | 取值 | 为什么 |
|---|---|---|
| 启用判据 | `current_asof()` 为真 | 实时路径零行为变更，且不需要额外开关 |
| 缓存键 | `version \| kind \| code \| pad_start \| eff_end \| adj` | 见下三条 |
| `eff_end = min(end_date, asof)` | **封顶后**的日期 | `get_wind_ohlcv` 在 as-of 下会把 `end_date` 截到 asof；键用截前的日期会让两个不同 as-of 的查询共用一份 |
| `adj`（个股 `hfq` / 指数 `na`）进**文件名**且进哈希 | 不只是哈希 | 前复权与后复权被每只票的常数缩放隔开，**混用不报错、只会静默算错收益**。写进文件名是为了"打开缓存目录一眼看懂"；指数线没有复权口径，所以标 `na` 而**不是**沿用 `hfq`——缓存目录是给人排查用的，不许在文件名上撒谎 |
| `kind`（`stk`/`idx`） | 隔离个股与指数线 | 两者形状相同、语义不同 |
| 空 frame | **一律不写** | 空可能是"真没行情"，也可能是一次被吞掉的瞬时故障。缓存下来会让该票在 TTL 内被永久判成无行情，而用户只看到一个标的数对不上、却查不出原因的回测 |
| 坏文件 / 过期 / 无 `Close` 列 | 一律当**未命中** | 缓存是纯加速层，坏文件绝不能让回测失败 |
| 写入 | 先写 `.tmp` 再 `replace` | 两个进程同时取同一只票时，读者不会看到半截 JSON |
| TTL | `BACKTEST_BARS_CACHE_TTL_DAYS`，默认 30 天 | 后复权 + 已收盘区间本不可变，TTL 只为兜住 Wind 侧数据修错 |

> ⚠️ **改动 `build_bars_from_frame` 或 `get_wind_ohlcv` 的任何取数口径**（量比窗口、停牌顺延、
> 复权方式、列名）**都必须把 `_CACHE_VERSION` +1**。旧文件会被原样读回来当新口径用，
> 而结果页上完全看不出来。加版本号 = 换一批文件名，旧的自然失效。

**副作用是好的**：预览的「检查数据」探数（§8）会把命中的日线写进缓存，所以**探数同时是给
正式起跑预热**——点过之后再起跑，取数那一步是零网络调用。

### 3.5 取数退避：判据是「重试有没有可能成功」

`backtest_data._with_retry` 对可重试的失败退避 2s / 4s / 8s，最多 3 次。**判据不是"错误文本里
有没有限流字样"**，而是服务端到底在说什么：

| 失败 | 重试？ | 为什么 |
|---|---|---|
| 限流（`VendorRateLimitError`） | ✅ | 等一会儿大概率就好 |
| 「服务暂时不可用，请稍后重试」 | ✅ | 服务端明说自己暂时不行。**实测 24 只里就有 1 只**——不重试它就成了"全程无行情" |
| **「单日请求次数超限」** | ❌ | 看着像限流，但额度**次日才重置**，退避 2s/4s/8s 全是白等 |
| 参数格式不对 / 鉴权失败 / 该票没行情 | ❌ | 重试多少次结果都一样，只会把失败拖慢 |

> 这张表的存在理由是**两个错误长得像、处理却相反**：额度耗尽和限流都写着"超限"，
> 但一个立刻停、一个退避重试。判据只能是语义。

配套地，起跑取数那一段外边包了一层 `_data_errors_as_user_text`（§8.5），
把厂商错误译成人话再显示到进度条上。

## 4. 撮合口径

**日内触发 + 跳空按开盘**（用户拍板）：

| 当日 K 线 | 选档标量 | `fill_price` | 结果 |
|---|---|---|---|
| `price_below: 8.90`，open 9.20 / low 8.80 | 8.80 | `min(9.20, 8.90)` = **8.90** | 触价成交 |
| 同上，open 8.60 / low 8.55（跳空） | 8.55 | `min(8.60, 8.90)` = **8.60** | 开盘价成交 |
| 同上，open 9.20 / low 9.10 | 9.10 | — | 不触发 |

**路径歧义**：日线无法还原当日 `high`/`low` 的先后顺序。价格维度取**更差**一端，数量维度走完
整条梯子——两处都按**不利方向**假设。

**子 tick**：`_pick_tier` 是**无状态**的（"当前持仓占比本身就是进度"），所以同一天内重复调用
`run_execution` 就会自动逐档推进。`HistoryClock.with_offset(k)` 只改 `ts`，`date`/bars 不变，
因此 `_get_today_plan(date=D)` 与 `_today_trade_count` 都算同一天，单日笔数额度跨子 tick 累积。
默认 `DEFAULT_SUB_TICKS = 3`。

**量比**：日线代理量比 = 当日成交量 ÷ 前 5 日均量。它用到**当日全天成交量（含日内事后信息）**，
会使 `volume_ratio_min` 档比实盘更容易被满足。Wind 没有可寻址的历史量比接口。

**涨跌停 / 停牌**：历史涨跌停价无接口可取，按板块静态规则近似（主板 10%、创业板科创板 20%、
北交所 30%、ST 5%、港美股不限）。停牌当日不交易，市值沿用停牌前最后有效收盘。

## 5. 逐日时序（必须严格镜像实盘）

实盘因果链是：**D-1 收盘后（15:05）跑 Stage1+Stage2 出 D 日的计划 → D 日盘中执行**。

```
research_date(D) = prev_trading_day(D)     # 计划 D 执行，研究用 D-1 收盘的信息
TrustPlan.trade_date  = D                  # 计划归属执行日，与实盘一致
EngineRun.trade_date  = research_date(D)   # 研究快照的时点标签
```

回测里每天的四个动作**顺序不能颠倒**：

1. 执行 D 日的计划（子 tick 逐档推进）
2. `trade.release_t1(sh)` —— **只在日终一次**，子 tick 期间不释放
3. 日终盯市，落 `BacktestStep`
4. 出 days[i+1] 的计划：Stage1 as-of D + Stage2

第 4 步放在盯市之后，是因为 `run_analysis_cached` 会把 `build_portfolio_context` 注入 Stage1 提示词——
它必须是"D 日执行完、按 D 日收盘价计"的持仓。**否则团队会拿着今天的仓位去分析半年前。**

> 第 0 天是**热启动日**：窗口之前不存在计划，`run_execution` 返回 `skipped="no_plan_backtest"`，
> 当天不交易。回测**绝不**回落到 `_execute_legacy` 的评级兜底路径——它读 `_get_latest_rating`，
> 会串日期。

**循环之前还有一道闸**（仅全新起跑）：数据完整性门禁（§8）在任何 LLM 调用之前判定，
`init_basis` 若被迫用成本价兜底也在这里拒绝起跑——分母错了，后面十小时全是白跑。

## 6. 收益口径

| 指标 | 口径 |
|---|---|
| 每日期末权益 | `cash + Σ(hold_qty × 当日收盘)`；停牌用最后有效收盘 |
| 起始基准 `init_basis` | `初始现金 + Σ(起始持仓 × 起始日收盘)` |
| 总盈亏 / 总收益率 | `equity(end) − init_basis` / `÷ init_basis` |
| 最大回撤 | `BacktestStep.total_assets` 净值曲线的峰谷最大跌幅 |
| 累计费用 | `Σ Trade.fee` |
| 已实现盈亏 | 加权平均成本法：每笔卖出 `(成交价 − 卖出前成本价) × 数量 − 费用` |

> ⚠️ **`init_basis` 必须用市价，不能用 `cost_price`**。copy 模式下持仓的 `cost_price` 是当前口径的
> 成本，拿它当分母会把**起始日之前的历史浮盈**算进"回测收益"。这是最容易写错的一条，
> `smoke_backtest_calc.py` 第 5 节专门守着它。

> `realized_pnl` 由 `backtest_calc.replay_realized` 逐笔重放 `trade.place_order` 的成本更新公式
> （含 `round(..., 4)` 与卖到零股清账），口径与库里的 `Position.cost_price` 对齐。
> **不要顺手去改 `trust.get_analytics`**——那是实盘接口，改了会改变前端与对话助手的既有语义。

**两个基准**：

- **等权买入持有（主基准）**：起始日按**开盘价**等权买入 universe，手数取整（A股 `//100`）与
  费用模型（`trade._calc_fee`）**与策略同源**，持有到期末。差异只剩"团队决策"本身。
- **沪深300（次基准）**：`000300.SH` 归一化到 `init_basis`，回答"这段行情本身如何"。
  它**不是**总收益口径（指数接口没有 `aftype`，见 §3.2），所以只当相对涨跌的参照物，
  不与策略做绝对对照——"团队比躺着不动强吗"这个问题由上面那条等权基准回答。

## 7. 断点续跑

`_execute_plan` 每笔都经 `place_order` 独立事务提交，无法整体回滚。所以用"快照 + 按 id 截断"：

- **检查点**：日终记 `{cash, positions}` + `max(orders.id)`。`positions` 必须连 `cost_price` /
  `available_qty` / `frozen_qty` 一起存——三者都影响后续定仓与 T+1。
- **恢复** `_restore_checkpoint`：① 删 `id > last_order_id` 的 orders/trades（半截残迹）+
  该日之后的 stale `BacktestStep`；② 用 blob 覆盖 `TrustConfig.available_cash` 与 `Position` 行。
  **幂等。**
- **起跑防双驱**：`worker_token`（`secrets.token_hex(16)`）CAS。进程启动时 `resume_orphan_runs()`
  把任何 `status='running'` 的行拉回来——本仓库是**单进程部署**，所以"启动那一刻还在 running"
  必然是上一个进程留下的孤儿。多进程部署下这个判据不成立，那时需要真正的心跳列。

`smoke_backtest_calc.py` 第 10 节把"跑一遍"与"崩在第 3 天再续跑"逐项比对：净值曲线、现金、
持仓、委托数、成交数、结果总量**全部相同**。崩溃用 `raise SystemExit` 模拟——进程被杀时解释器
根本没机会跑任何 `except` 分支，`BaseException` 是唯一忠实的模型（`_drive` 里按天兜的是
`Exception`，那是给单日行情抖动用的，两者不是一回事）。

## 8. 起跑前的数据完整性门禁

`load_bars` 对单只失败是**记一条 warning 然后继续**——这在取数层是对的（一只票取不到不该废掉
十小时的长跑），但**如果没人把 warnings 收口**，用户看到的就永远是"标的 45 只"，而实际只有
40 只在跑。那不是回测，是**静默的样本替换**。最坏的一种错最不可辨：一只都没取到时，跑出来的
"团队全程没交易"和"团队判断该空仓"在结果页上**长得一模一样**。

所以设两道门禁，**都在任何 LLM 调用之前**：

### 8.1 门禁一：标的池（`_data_gate`）

| 情形 | 处置 |
|---|---|
| 标的池为空 | 拒绝，指向自选股与选股范围 |
| 一只都没有 | 拒绝，且**必须点明**它和"团队判断该空仓"在结果页上长得一样 |
| 缺失 **超过一半**（`missing / total > 0.5`） | 拒绝，并说清还剩几只可跑——"这已经不是你所选的那个标的池了" |
| 缺一两只 | 放行。为一只停牌票拦下一次十小时长跑是过度设计，如实标注实际参与数即可 |

阈值是**严格大于**一半，边界值不能被悄悄挪成 `>=`（`smoke_backtest_calc.py` 第 12 节钉住了
"恰好缺一半仍放行"）。

> 门禁一**只在全新起跑时**判定。续跑已经烧掉几小时的 LLM，数据在两次尝试之间变化更可能是
> 一次瞬时抖动，为它废掉已完成的十天不划算——那时候按警告放行，由结果页如实标注（§8.4）。

### 8.2 门禁二：起始持仓的分母（`_basis` 的 `unpriced`）

`init_basis` 必须用**起始日市价**（§6），所以起始持仓里任何一只在起始日取不到行情时，
`_basis` 只能退回 `cost_price` 兜底——而**退回成本价恰好会把起始日之前的历史浮盈算进回测收益**，
分母一错，总收益率整条都是错的。

所以 `_basis` 通过 `unpriced` 出参把"兜底过的票名"回传出来，调用方**据此拒绝起跑**，
并给出三条出路：把起始日期往后挪到它们有行情的那段 / 改用「空仓起步」/ 先把这几只调出托管簿。

### 8.3 预览探数（`probe=1`）

分析是几十只票 × 十几个交易日，等十小时后才发现有票没数据，代价是一条已经跑完的长任务。
所以预览提供一个**显式**的「检查数据」按钮：真取一次数，把「45 只里 40 只有数据」摆在发起之前。

- **复用同一个 `_data_gate`**，不复制判据——预览说"能跑"而实际被拦下，比不预览更糟。
- **`init_mode == "copy"` 时另算门禁二**：读的是**真实托管簿**的持仓（起跑时复制过去的就是这批
  `hold_qty > 0` 的行），把"起跑后必被拦下"提前到点按钮之前。空仓起步不会误伤。
- `blocking` 为真时前端**禁用「开始回测」**并把 `block_reason` 放进按钮 `title`，同时把拒因排在
  `warnings` 的**最前面**——排在"建议先跑试点"后面会被读成又一条建议。
- **不探数时这些字段留空而不是留零**：`probe=False` / `data_available=None` 表示"没查过"，
  和"查了没问题"在 UI 上长得一样，但后者是在替后端打保票。没依据就不许在 UI 上禁用按钮。

> **代价**：预览要花 N 次 Wind 调用、多等几十秒，所以它是个显式选项而不是默认行为——预览按钮
> 不该突然变慢。取回的数据落进 §3.4 的磁盘缓存，**探数顺带就是给正式起跑预热**。

### 8.4 结果页必须如实标注（不只在起跑前）

跑起来之后缺失依然可能发生（续跑不再走门禁一，数据在两次尝试之间变化更可能是一次瞬时抖动，
为它废掉已完成的十天不划算）。所以 `result_json` 永远带上
`universe_requested` / `universe_loaded` / `missing_symbols`，前端在 KPI **上方**单起一块
告警栏渲染：标题写「标的池未跑满：请求 45 只，实际参与 40 只」并列出缺失标的，
副标题同步显示「标的 40/45 只」。

> 那声明（§11）是**口径**说明，这块是**这次运行的事实**——两者不能互相替代，
> 混在一起就会被当成又一条模板文字划过去。

> ⚠️ **门禁拦不住幸存者偏差。** 取不到行情的票多半是长期停牌或已退市的——把它们剔掉再跑，
> 剩下的池子天然偏向"活到今天"的标的，而回测区间的起点在过去。这是第 6 条事后选样偏差
> （§11）的一个更隐蔽的变体，产品上只能靠**如实列出缺失标的**让用户自己看见，
> 没有"自动修正"这回事。

### 8.5 取数失败要译成人话（`_data_errors_as_user_text`）

起跑取数那一段（`_drive` 与 `preview`）外边包了一层翻译：厂商错误 → `ServiceError`
的**中文结论**，厂商原文退成括号里的附注。原因是那行字会原样显示在进度条上，而
`VendorRejectedError: Wind index_data/get_index_kline 返回：单日请求次数超限`
既不告诉用户"这是额度不是 bug"，也不告诉他"要等次日"——最可能的反应是反复重试。

三条口径，都钉在 `smoke_backtest_calc.py` 第 12 节：

| 情形 | 译法 |
|---|---|
| Wind **每日额度**耗尽 | 「今日额度已用完，要等次日重置」，并说明回测为何对额度敏感 |
| 鉴权失败 / 余额不足 | **不猜原因**，原样保留厂商原文——猜错比不猜更耽误人 |
| 基准整段无 K 线（`NoMarketDataError`） | 「请换一段区间」 |

**额度耗尽必须当场失败，不能降级**：额度没了，交易日历第一个取不到；即便绕过它，后续每只票
的日线、以及分析时的行情工具也全会失败——那种"跑完了但团队全程没数据"的结果页，
比直接失败危险得多。

> **为什么额度耗尽不走退避重试**：它长得像限流，但落在 `VendorRejectedError` 上，
> 而 `_with_retry` 只认 `VendorRateLimitError`。这是**故意**的——额度要到次日才重置，
> 退避 2s/4s/8s 只是把失败拖慢三次然后照样失败。**区分标准是"重试有没有可能成功"**，
> 不是"错误文本里有没有限流字样"。

## 9. 接口与前端

```
POST   /api/backtest/run                  → {run_id, trading_days, est_label}
GET    /api/backtest/list
GET    /api/backtest/preview?start=&end=&probe=&init_mode=&bt_scope=&bt_groups=
                                          → 交易日数、标的数、预计调用次数与耗时、告警；
                                            probe=1 时真取数并回传 data_available/data_missing/
                                            missing_symbols/missing_held/blocking/block_reason；
                                            bt_scope 非空时另回传 range_label / merged_holdings
GET    /api/backtest/{run_id}             → 进度（status/stage/message/done/total）
POST   /api/backtest/{run_id}/cancel
GET    /api/backtest/{run_id}/result      → 聚合 + 基准 + 声明 + 逐日 step
GET    /api/backtest/{run_id}/trades      → 逐日成交明细（按模拟日分组；前端「成交明细」卡片）
GET    /api/backtest/{run_id}/reports     → 日期清单 = **这个 run 真实跑过的交易日**
                                            （以 BacktestStep 为骨架，不是"有计划的日期"）；
                                            每条含 has_plan / plan_missing_reason
                                            （first_day = 首日无前置研究日属设计；missing = 环断了）
GET    /api/backtest/{run_id}/report?date=&inline=
                                          → 该日的流程报告 HTML（与实盘同一渲染器）
GET    /api/backtest/{run_id}/monitor?date=YYYY-MM-DD
                                          → 该日的监控条件卡片（**执行口径**：卖/减看当日最低、
                                            买/建看当日最高，与撮合同一判据）；
                                            该日无计划 → has_plan=false + reason，**不打 Wind、不返回假数据**
DELETE /api/backtest/{run_id}             → 连带删掉本 run 窗口内的计划（§2.6）
```

> ⚠️ 前三条**必须声明在 `/api/backtest/{run_id}` 之前**。Starlette 按声明顺序匹配，通配的那条
> 放前面会让 `list` 被当成 `run_id="list"` 吃掉。

- **每一条读接口都过 `_require_own`**（`run_id + user_id == owner` 双条件）。回测表按 user_id
  分区，越权读别人的回测等于把别人的持仓与决策过程全抖出来。`smoke_backtest_calc.py` 第 11 节
  逐条验越权被拒。
- **删除回测不删影子账户**：后者承载 `EngineRun` 研究缓存（30 天 × 5 只 ≈ 600 次 LLM 调用，
  十小时量级）。删掉等于把最贵的东西扔了。
- **前端不复制任何口径**：声明、基准、逐日净值全部来自后端 `result_json`。复制一份的下场是
  两边悄悄漂移，而"回测结果"这种东西一旦漂移就完全不可信了。

### 9.1 回测股票范围（`bt_scope` / `bt_groups`）

回测页面能选「要回测的股票范围」——**持仓股 / 自选股二选一**；选自选股时可多选分组
（一个都不选 = 全部分组）。

```python
BT_SCOPE_HOLDINGS  = 0   # 发起人的托管簿持仓（book == 1 且 hold_qty > 0）
BT_SCOPE_WATCHLIST = 1   # 发起人自选里 group_name ∈ bt_groups 的票（bt_groups 空 = 全部分组）
```

`backtest.resolve_range(owner_user_id, bt_scope, bt_groups, init_mode)` 返回
`{codes, names, merged, missing_groups, label}`：

- **`init_mode == "copy"` 时自动并入发起人全部持仓**，`merged` 就是被并入的那几只
  ——用户选定"复制当前持仓"但范围里不含某些持仓时，**自动并进来并在预览里标注**，
  而不是悄悄少几只票（那是"账对不上但看不出来"的经典形状）。
- **`bt_groups` 里的组已不存在 → 跳过并在 `label` 里如实说明**；但如果**选中的分组一个都不存在，
  结果是空池而不是"没筛选"的全量池**——`resolve_range` 用 `requested`（用户要什么）与
  `wanted`（实际存在什么）两个变量把这两种情况区分开。少了这一层，"静默多跑十几只票"是必然的。
- **刻意不复用 `stock_scope` / `stock_scope_group`**：那两个键是**发起人托管设置**的范围，
  与"这次回测拿哪些票跑"是两件事。把它们混起来正是 §2.3 那个缺陷的形状
  （**校验读的键 ≠ 执行读的键**）。本次另用 `bt_scope` / `bt_groups` / `bt_names` / `bt_merged` /
  `bt_range_label`，一起冻进 `config_json`。
- **服务端解析，预览与起跑同源**：`api_backtest_run` 自己调 `resolve_range`，
  不接受前端算好的池（前端算的话，"预览说 8 只、实际跑 12 只"是必然，而且查不出来）。
  `req.universe` 仍然更高优先级，兼容既有调用与测试。
- `bt_scope is None` → 沿用旧的 `get_analysis_universe(owner)` 路径，**一个字不动**
  （既有的 15 条 preview 断言因此零回归）。
- 前端：范围胶囊 + 分组多选行（数据来自**已有的** `/api/watchlist/groups`，不加新接口）；
  预览显示 `range_label` 与「已自动并入 N 只持仓股」；**范围为空时直接禁用「开始回测」按钮**
  并把原因挂在 `title` 上，而不是让用户点了才在 toast 里被拒。

### 9.2 回测流程报告（按计划生效日）

回测跨多个交易日、每个交易日一份次日行动计划，所以「查看回测里的报告」只比实盘多一件事：
**按日期取**。为了做到"结构和实盘『次日行动报告』一样"，报告正文**不新写一份渲染器**，而是
直接调实盘的 `plan_report.render_plan_report`——格式一致靠"同一个函数 + 同形的入参"，
不靠两边各画一遍版式（那样迟早漂移）。

- **数据源是影子账户的 `TrustPlan`**（唯一键 `user_id + trade_date`），不是发起人的。
  所有权校验走 `_require_own`，取数据用 `run.shadow_user_id`——两件事不能混，
  混了就是"一条计划都查不到"。
- **账户快照取"计划生成那一刻"的账**，即 `trade_date < D` 的**最后一个** `BacktestStep`。
  计划是研究日 D−1 盘后产出的，报告必须配那一天收盘的账。抄 `get_plan_download_data`
  那套（读**当前**持仓）会让 09-09 那份计划显示"0 持仓 + 38 条建仓动作"，一份自相矛盾的报告。
  没有前序 step 时退到 run 的起始状态，并回传 `as_of_source="initial"`，**不假装**那是某天的收盘账。
- `BacktestStep.positions_json` 里没有 `assets_ratio`（那是账户层算的），取数时按
  `市值 / 总资产` 补齐——否则报告的「占比」列恒空。
- **没有冻结研究快照时绝不回落实时查库**：`collect_research_snapshot` 不带研究日会取
  "最近一次" `EngineRun`，而影子的研究结果跨研究日累积，那可能是**更晚**的日期，即未来函数。
  宁可如实报"这份计划没有研究依据"（`research={}` + `research_missing` 列全），也不给一份
  日期对不上的研究报告——报告的用途正是判断"团队当时凭什么下的这个决定"。
- **"有计划、没 step" = 这一天没跑到**（计划落库在前、step 落库在后，研究跑完才存 step）。
  `executed=False` 会一路传到前端，在日期下拉和说明文字里都点出来，否则一份从未被执行过的
  计划与跑完的那天**长得一模一样**。
- **横幅是纯叠加**：`render_plan_report(..., banner=...)` 只在标题下多插一段 `<div class='warnbox'>`。
  默认空串 ⇒ 实盘输出与加这个参数之前**逐字相同**（有断言钉着）。回测用它标注
  「本报告来自历史回测 run #N（模拟撮合，非实盘成交）」——没有它，一份回测报告落到人手里
  是看不出来它没在实盘执行过的。
- **前端只做两件事**：挑日期、把后端给的 HTML 用 blob URL 塞进 iframe。不走 `iframe.src=` 是因为
  报告接口要 `Authorization` 头，iframe 发不出。所以「内嵌预览」与「下载」是**同一份字节**，
  连报告里的标签页与「展开明细」按钮都能用。

### 9.3 已跑时长（"这次到底跑了多久"）

一个十小时量级的长任务，界面上却**一个时间都不显示**：`BacktestRun` 有 `created_at` /
`finished_at`，前端从未渲染。用户只能去翻库——而这恰恰是决定"要不要再来一次"的那个数。

- **口径只有一条：跑完取 `finished_at`，在跑取"现在"。** 取数点收在 `_elapsed_seconds`，
  `get_progress` 与 `list_runs` 共用。
- **在跑不能取 `updated_at`**：那是进度心跳的时间，一个卡住十分钟的 run 会把已跑时长
  **冻在十分钟前**，界面看着像"没动"（实际还在跑）；反过来拿它当"现在"，时长就永远追着心跳走。
  在跑只能用墙上时钟算，这样 UI 每轮询一次就往前跳一格——那才是"正在跑"的体感。
- **拿不到就不显示**：`created_at` 缺失（口径升级前建的老记录）→ 后端给 `None` / `""`，
  界面整段省略，**不写 `0`**。沿用本项目"宁可 `None` 也不要一个看起来像结论的 0"的既定立场。
- **措辞与预估共用 `_human_duration`**：取数前给的预估是「约 2.3 小时」，跑完给的实际也必须是
  「约 2.3 小时」。预估和实际用两套说法（一个"约 2.3 小时"、一个"8280 秒"），用户就没法把它们
  对起来——而"把预估和实际对起来"正是这个数唯一的用途。
- **前端 `BT_TERMINAL` 收成一处**：进度条（终态必须禁用取消按钮）与列表（说"用时"还是"已跑"）
  共用同一个终态清单，两处各写一份的话，将来加了新终态必然漏掉一边。
- 进度计数由「6 / 15 个交易日」变为「6 / 15 个交易日 · 已跑 约 12 分钟」，终态改口「用时」
  （结论）——同一个数，在跑是"当下的等待"，跑完是"结论"。时间戳也会夹到 0，时钟回拨不出负数。

### 11.1 首日不可执行是**保真缺口**，不是"就这样"（2026-09-12 记录，本次不改）

第 12 条描述的是**设计**（首日无可执行计划），但设计之下还埋着一个**保真缺口**：
`trust._run_execution` 在回测路径遇到"没有计划"时直接返回
`{"trades": [], "skipped": "no_plan_backtest"}`，**不会回退**到 `_execute_legacy`；
而实盘在无计划时**会**走评级兜底那条路。于是首日除了"没有计划"之外，还少了实盘真实存在的
兜底动作——两层原因叠在一起，首日必然是空转的。

**为什么不改**：改动点在执行入口，与实盘共用同一段函数，而 2026-09-14（周一）要用真实盘中
触发来验收实盘路径（见测试报告的 B 组用例）。为了回测首日一天的表现去动实盘执行入口，
风险和收益不成比例。**记录在此，等实盘验收通过后再评估。**

**验证工具侧的对齐**（这条已改）：`scripts/score_backtest_run.py` 的"风控纪律"原先会把
**首日的继承状态**记成团队违例——实测 run 4 的三条违例全部落在首日（两条超配 + 一条由 §2.9
的复权口径造成的假浮亏）。首日既然无可执行计划，团队那天**没有任何手段**去减仓，用它扣分
等于用起跑线的位置判失职。现在首日的**持仓类**违例单列在 `inherited_violations` 里、
说明"首日·起始状态，当天无可执行计划"、**不计分**（照 `梯子合理性` 里"首日没有研究日，
跳过"的同一先例）；成交笔数上限仍全量判——它在首日天然为 0，豁免与否不改变结果。

### 11.2 这次改动对**实盘**的影响（部署须知）

**§2.9（2026-09-12）对实盘零影响**：`_rescale_copied_book` 只在 `init_mode=copy` 且**全新起跑**
时被调用一次，改的是影子的持仓行；实盘的报价与成本价**同为不复权**（`_execute_legacy` 是
raw-vs-raw），口径本来就一致，不需要也不应该换算。新增的 `load_unadjusted_closes` 是只读的
取数函数，不改变任何撮合行为。

§2.3 只影响回测（影子账户），**§2.4 会改变实盘的真实交易行为**——两处共用同一段
`build_portfolio_plan_context`，没有开关。部署后：

- 实盘团队**将首次能够买入选股范围内的新标的**（此前只有空仓那一种场合能买）。
  这不是 bug 修复的副作用，而是"选「自选股」本该生效"的兑现。
- **止血方式（无需发版）**：把托管设置的**操作股票范围改回「仅持仓股」**，
  `get_managed_symbols` 就只返回持仓，【候选】段自然为空，行为立刻回到改动前的样子。
  **选股范围就是这次改动的开关。**
- 已知限制（本次**不改**，只记录）：`stock_scope=2` 在界面上显示为「全市场」，
  但 `get_managed_symbols` 实际只取**持仓 ∪ 自选**（`trust.py` 的 scope 分支），
  并不是真全市场。这一条与本次改动无关，是既有的名不符实。

**§2.10（2026-09-13）会改变实盘的一条报错文案，不改行为**：`app/trust.py` 的取计划处新增
`except AccountLevelLLMError`，把「LLM 账户不可用（HTTP 402: Insufficient Balance）：请检查
API key 与账户余额」与既有的「这次没拿到结构化结果，请稍后重试」**分开**。触发条件从
「任何异常」收窄为**只认 401/402**（429 限流与 403 权限**仍然走原来的"稍后重试"路**），
所以实盘的行为面**只会变小**：原先那种"余额没了却提示稍后重试"的误导消失了，其余一切照旧。
️ ⚠️ 与 §2.4 不同，这一条**没有反向开关**——它只在报错那一刻生效，不影响下单与撮合。
