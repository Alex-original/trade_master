# 多档触发（价格阶梯 + 量能条件）：设计与判定口径 v1.0

> 适用范围：`product/trade_master` 的 AI 托管执行层（`app/trust.py`）。
> 相关测试：`docs/测试用例_模拟交易AI托管_v0.1.md` 的 **TM-M7-20 ~ TM-M7-31**。
> 可执行回归：`python scripts/smoke_ladder.py`、`node scripts/check_frontend.js`。

---

## 1. 为什么需要它

改造前，一只票的次日计划里只有**一条**条件化动作（`ConditionalAction` 只有一个
`trigger_type` + 一个 `trigger_price` + 一个 `target_weight`）。2026-09-11 生产的真实计划里
写的是这样一句话：

> 「条件止损：放量跌破 8.90 先减约 1/4 至约 13.8%；有效跌破 8.76–8.82 支撑带再减至半仓
> 以下（<9.2%）；硬止损 8.75。」

09:26 价格 8.895 触发第一档，执行层正确地卖到 13.8%——但**后面两档和「硬止损 8.75」
永远不会执行**，因为它们只存在于 `reason` 这段散文里；「**放量**」这个限定词同样无处判定。
把风控条件写进理由、指望人或模型后续再处理，等于没有风控。

改造后的目标：一只票可以有一整套**由浅到深的分档触发**（梯子），每一档都带自己的价格阈值、
量能门槛和目标占比，执行层逐档真的会执行；界面（报告 + 监控卡片）如实展示走到哪一档。

---

## 2. 数据模型：同 code 多行，不引入嵌套

**一只票的多档 = 计划 `actions` 数组里同一个 `code` 的多条动作行。** 不新增 `tiers:` 嵌套字段、
不改数据库（`TrustPlan.plan_json` 是不透明 JSON 列），只给每行加一个可选字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `volume_ratio_min` | `float \| None` | 量能门槛：**量比 ≥ 该值**才算满足（`None` = 不限）。与价格条件**同时成立**才触发。「放量跌破 8.90」写成 `trigger_type=price_below, trigger_price=8.90, volume_ratio_min=1.5`。 |

为什么沿用「同 code 多行」这个形状：`normalize_plan_actions` 的去重键本来就是四元组
`(action, trigger_type, trigger_price, target_weight)`——**不同 `trigger_price` 的多行本来就会被保留**。
真正要改的只有两件事：（a）给每行加量能门槛；（b）把四处 `{code: a}` 的字典推导（会把同 code
的多行压成一条）改成「按 code 分组 + 按方向排序」。

---

## 3. 分档的归组与校验（`app/plan_actions.py`，纯函数）

一只票的多行先按方向拆成**两条梯子**：`exit`（减仓梯子，`reduce`/`sell`）与
`entry`（加仓梯子，`buy`/`add`），时间型档位（`none`/`open`/`intraday`）作为该方向的
无条件基准档。**允许双向**：同一只票可以同时挂减仓梯子和加仓梯子。

每档按「深浅」排序：`price_below` **触发价越低越深**，`price_above` **越高越深**，时间型恒为最浅。

### 校验规则

| 规则 | 说明 | 违反时 |
|---|---|---|
| 同向 | 一条梯子内只允许同一族动作（减仓梯子只有 `reduce`/`sell`） | 截断 + 告警 |
| 单调 | 由浅到深，减仓梯子 `target_weight` **不增**、加仓梯子**不减**（越深越保守） | 截断 + 告警 |
| 触发价有序 | 同梯子内允许重复阈值（见下），但顺序必须由浅到深 | 排序修正 |
| 死档剔除 | `price_below`/`price_above` 却没有 `trigger_price` 的档永远不可能触发 | 丢弃 + 告警 |
| 最多一个时间型档 | 多个「开盘即执行」语义上等价，只留最后一个 | 丢弃前面的 + 告警 |
| 双向不打架 | `max(减仓梯子触发价) < min(加仓梯子触发价)`，否则同一价位既买又卖、来回对冲白付手续费 | 保留减仓梯子、丢弃加仓梯子 + 告警 |
| `sell` ⇒ 目标 0 | 字段定义 sell = 清仓；否则会出现「卖到 3%」这种永远清不掉的零股 | 强制 `target_weight = 0.0` |

### 截断而不是整只丢弃

出现非法档时保留**最长的合法前缀**，丢弃出错的档及其之后所有档，原因写进
`plan["process"]["ladder_warnings"]`（在 JSON blob 里，无需迁移），报告的口径说明下方如实列出。
理由：因为第 3 档格式错就把第 1 档一起丢掉，等于**关掉唯一可执行的档**，比「梯子变短」更糟。

### 与原始方案的一处偏离（实现时判定）

设计稿写的是「同梯子内 price 阈值不得重复」并按**截断**处理。实现时改为**只告警、不截断**：
重复阈值的两档在 `_pick_tier` 下能正确逐档推进（第一档达到目标后，第二档因「目标尚未达到」
而继续生效），截断反而会关掉一档可执行的条件。这里是「警告但不作为」，与上面的
「截断而非整只丢弃」同出于一个原则——**别把可执行的档关掉**。

### 写时也跑一遍

`app/analysis_service.py` 在落库前调 `sanitize_ladder_actions(...)`，所以**存进库的 blob
本身就是排好序、校验过的规范形态**（同 code 多行保留，非法档已剔除）。读时（执行层 /
监控卡片 / 报告）再各跑一次 `build_ladders` 作为防御，兜住历史计划和手工改过的 JSON。

## 4. 执行语义（`app/trust.py`）

### 4.1 逐档分批，无状态

`_pick_tier(tiers, kind, price, volume_ratio, current_weight)` 返回
**最浅的「条件已满足、但目标尚未达到」的那一档**，没有则返回 `None`。

「目标尚未达到」直接用**当前持仓占比**判断（容差 `_WEIGHT_TOL = 0.002`，吸收整手取整误差）：

- 减仓梯子：`current_weight > target_weight + tol` 才算未达到；
- 加仓梯子：`current_weight < target_weight - tol` 才算未达到。

因此**不需要持久化「已执行到第几档」**——当前占比本身就是进度。由此天然得到逐档分批：
价格停在 8.70（穿越三档）时，tick 1 卖到 13.8%、tick 2 卖到 9%、tick 3 清仓，每分钟推进一档，
**每 tick 每只票最多一笔委托**。

浮点容差是必要的：`0.138` 这类目标占比对应的股数经整手取整后，实际占比往往是 `0.138001…`，
用严格等号会导致同一档被反复判定为「未达到」而重复下单。

### 4.2 统一时间闸门：所有触发档一律 ≥09:30

`_market_open(now=None)` 是唯一的判定处，**对所有触发类型生效**（不再只有 `open` 特殊）：

```
t = action.trigger_type
future = monitor_date 晚于今天

if future and t in (none, intraday, open):  return False   # 展示的是下一日的计划
if not future and not _market_open():       return False   # 新增的统一闸门
```

两个理由：`量比` 在**连续竞价开始前没有意义**（9:15–9:25 只是集合竞价）；更要紧的是
**价格型档位原本完全没有时间闸门**，而调度器是 `CronTrigger(day_of_week="mon-fri", hour="9-14", minute="*")`
——**09:00 起就在跑**。

**唯一例外（刻意保留）**：监控日期**晚于今天**时（即卡片在预演下一日的计划）不加闸门，
卡片继续按当前价如实显示「条件是否已满足」。那不是漏判——该计划今天根本不会执行。
这条差异写在代码注释里，免得以后被当成 bug 修掉。

### 4.3 单日笔数上限：清仓档不占额度

规则：**只有「把仓位调到非零目标」的成交才消耗额度**；`target_weight` 为 0 的档（清仓）
与走止损路径的成交都**不占额度**。

```python
cap = cfg.risk_max_trades_day or 0
budget_exhausted = bool(cap) and budget_used >= cap

def _spend():                       # 每笔**非清仓**成交后调用
    nonlocal budget_used, budget_exhausted
    ...
```

为什么要这么绕：原来额度耗尽处是 `return {"trades": ..., "skipped": "max_trades"}`
——**直接退出整个函数**。一旦额度在遍历到某只票时耗尽，排在它后面的清仓档就被一起 return 掉了。
所以这里改成：

- 挑档前先过滤：`if budget_exhausted: tiers = [a for a in tiers if not a.get("target_weight")]`
  ——额度用尽后**只剩清仓档可选**，循环继续往下走；
- 买入循环整体被 `if not budget_exhausted` 拦住（买入永远不是清仓）。

效果：一次跳空穿越三档时，最深的清仓档**永远不会被上限卡住**；同时额度对非清仓档仍然有效。

**已知边界（刻意）**：额度用尽后仍会遍历全部持仓去执行清仓档，所以「跳空当天把所有票一次
清完」可以在同一 tick 发生。清仓优先于「限制换手」这个目的。

### 4.4 额度播种

`run_execution` 用当日**已成交笔数** `_today_trade_count(user_id)` 播种 `budget_used`
再进入 `_execute_plan`，避免同一交易日内多次 tick 各自从 0 起算而绕过上限。
播种值包含当日已发生的清仓成交（偏保守但安全——「清仓档不被挡住」这个前向性质仍然成立）。

无计划时（旧评级路径）保持原来的早退语义不变。

### 4.5 其它

- **止损优先级不变**：用户显式设置的硬止损仍高于计划，走独立分支，不受梯子校验影响。
- **T+1**：清仓档在 `available_qty < hold_qty` 时只卖可用部分，下一 tick 因「目标未达到」
  继续重试直至卖完——这正是逐档分批想要的行为，无需特殊处理。
- **整手**：`app/trade.py` 只对买入（`direction == 0`）校验 `% 100`，卖出不受整手限制，
  零股可清干净。

## 5. 量能取数链路（`量比`）

1. `engine/tradingagents/dataflows/wind.py`：`get_price_snapshots` 的 `indexes` 带上 `量比`，
   按列名取值并经 `_to_float` 容错解析（`'', 'null', 'nan', '-', '--'` 一律 `None`，不抛）。
2. `app/account.py`：行情缓存元组扩宽一位带上 `volume_ratio`；执行层、监控卡片、账户页
   共用同一个 `get_quotes` fan-in，只改一处。
3. 由调用方把 `volume_ratio` 传进 `_trigger_satisfied` / `_pick_tier`。

**字段口径**：这台 Wind MCP 服务器的指标字段是**封闭词表**，`量比` 才是指标口径；
`五日平均成交量` 会被拒绝（`Invalid value ... for field`）。

**取不到时一律判为不满足（fail-closed）**：绝不退化成「纯价格」——否则会在最需要量能确认的
时刻悄悄变成最激进的执行。

## 6. 消费端（三处 + 前端）

| 位置 | 行为 |
|---|---|
| `app/trust.py::_execute_plan` | 按梯子逐档推进（见 §4） |
| `app/trust.py::get_monitor_conditions` | **逐档一行**：每行带 `tier_index`/`tier_count`/`is_first`/`kind`/`volume_ratio`，每档有自己的 `triggered`；顶层 `code_count` 是**标的**数（≠ 行数），供前端副标题用 |
| `app/plan_report.py` | 第一章行动表**一只票一行**：触发条件列用 `<br>` 把各档编号堆叠（`1. 跌破 8.9（量比≥1.5）→ 13.8%`），目标占比列显示档位序列；§3.0 速览只给最浅档的 tag + 档数 |
| `app_frontend/index.html::loadMonitorConditions` | 逐档一行，第 2 档起是续行（`└ 第N档`，组内虚线分隔、组末实线）；副标题 `N 只标的 / M 档条件` |

**向后兼容**：单档计划（以及所有没有 `tier_*` / `volume_ratio_min` 字段的历史计划）在四个
消费端的渲染结果与改造前**逐字一致**——前端把缺失的 `tier_index` 当 0 处理。
`scripts/check_frontend.js` 与 `scripts/smoke_ladder.py` 都在断言这一点。

## 7. 生产端：让模型真的写出梯子

结构化输出的字段描述（`portfolio_schemas.py` 的 `_TIERS_HINT`）与三个提示词
（`portfolio_team.py` 的 `_analyst_prompt` / `_risk_prompt` / `_pm_prompt`）都要明说：

- 同一只标的**可以给出多条动作行**形成分档，同向、按触发价由浅到深、越深越保守；
- 每档填该档触发后要达到的**绝对**目标占比（不是增量）；
- 要表达「放量」就在该档填 `volume_ratio_min`；
- **组合经理不得把草稿里合理的梯子压平成一条**——把多档写进 `reason` 的散文里等于不会执行
  （执行层只认 `actions` 里的多条动作行，`reason` 只给人看）。

风控官的审查清单里加了「逐只核对梯子」与「同一只票不得给出会互相打架的双向梯子」。

## 8. 部署与风险

- **无 DB 迁移**：计划 schema 是不透明 JSON；`ladder_warnings` 塞在 `process` 里。
- **提示词与 app 必须同镜像上线**：若「新引擎（含新提示词）」先于「新 app」生效，新引擎产出的
  多行计划被**旧 app** 读取时，`{code: a}` 会留下**最深那档并当场执行**——等于任何价格都直接清仓。
  代码烤进同一个镜像（`COPY app/ app/`、`COPY engine/ engine/`），正常部署不会错配。
- **`max_tokens` 共享预算**：`app/analysis.py` 固定 8000，`deepseek-flash` 的隐藏推理 token 与之共享；
  分档会放大组合经理的结构化输出行数。失败时结构化输出退化成空 actions → 回落到旧的评级执行，
  **安全但静默**。上线后第一周应盯结构化失败率，必要时上调 `DEEPSEEK_MAX_TOKENS`。
- **逐档分批在天数上的暴露**：跳空后每分钟推进一档，若当日休市或行情中断，仓位可能停在中间档
  （例如卡在 9.2%）。这是「逐档」语义的固有代价；靠**清仓档不占额度**保证最坏情况仍能走完。

```bash

.venv/bin/python scripts/smoke_ladder.py        # 68 项

# 前端监控卡片渲染 + 重贴覆盖提示（把 index.html 的内联脚本放进最小 DOM 桩里跑）

```

三个脚本都不需要 Postgres、不需要 Wind、不需要 API key，可以直接进 CI。
