- **G3 无手动下单/手动触发执行端点**（❌ 已闭环，见上方更新）：撮合与托管执行只能由调度 cron（工作日）或 **脚本直调** `trade.place_order` / `trust.run_execution`。UI 层无买/卖按钮。
- **G4 风格档不直接参与执行（单票上限参与）**：订正 v0.1 原文——`risk_max_position_pct` **已参与执行**：`app/trust.py:623` 把它当作买入的单票占比上限（在 `_execute_plan` 的买入分支里截断目标仓位，E2E 用例 `TM-M7-08` 覆盖）；只有用户**显式设置**时生效，未设置（`None`）= 不限制。仍成立的是 `style`（保守/均衡/进取）：执行层不读它，它只经 `app/trust.py:165` 进入组合决策上下文，因此**影响的是计划怎么被生成、不是执行怎么被放行**。→ 加仓/建仓用例可按 `risk_max_position_pct` 断言截断，`style` 只测读写回显与「确实进了计划上下文」。
- **G5 涨跌停判断是近似值**（❌ 已闭环，见上方更新）：A股按“最新两日涨跌幅 ≥ ±9.5%”近似（主板），创业板/科创板 20% 未精确区分；停牌/无行情走 Wind，可能返回“暂不可交易”。→ 现在改按板块精确规则 + 「成交价是否到板价」，`scripts/smoke_limit_rules.py` 62 项逐档钉死；但**仍缺真实涨停股的实弹跑**（需交易日出现涨停标的）。
- **G6 真短信未通**：移动/电信报备未完成，登录验证码全部走“打印日志”开发兜底。
- **G7 截图 OCR 只测过合成图**：真实券商 app 截图排版多变，需人工实测若干张后再定阈值；qwen3-vl-flash 单次约 2–5s。
- **G8 托管簿无现金买入受限**：托管簿现金恒 0、换仓式，买入依赖“先卖出产生现金”。纯“评级买入、无任何可卖持仓”场景不会产生买。

#### 14.3.3 托管团队能力打分（回测可信之后才做；这不是管线测试）

> 目标是回答**"这个团队值不值得用"**，不是"跑得通不通"。只读 step 快照
> （`plan_json`/`positions_json`/`trades_json`），所以**是按 run 隔离的**，天然可复用。

| # | 维度 | 判据 | 写脚本时踩到的坑（已修） |
|---|---|---|---|
| 1 | **覆盖率** | 每个在管标的**是否都有明确结论**。按**当天动作覆盖的去重标的数 / 标的池**量 | ⚠️ **不能用 `research_missing`**：`process.research` 只是「计划动作涉及的 code ∪ 持仓」的**截取快照**，逐日**恒等**于"涉及标的数"，它常报 0 —— 拿它当覆盖率会把正常情况报成覆盖不足，**又会漏掉真问题**（实测有整天只对 7/23 只表过态、连一条 `hold` 都没有） |
| 2 | **依据性** | 每条动作的 `reason` 能否追溯到研究报告（**不接受"凭名称下注"**） | 理由为空的条数、中位字数、退化 `risk_notes`（实测见过 `'【错因"].'`，属 LLM 结构化输出噪声，不是代码缺陷） |
| 3 | **梯子合理性** | 触发价相对现价的**距离分布**——不该出现"触发价离现价 30%"这种不可达档 | ⚠️ **参照价必须是研究日收盘，不是执行日收盘**：计划在 d 日日终用 d 日收盘价做出、d+1 执行。拿 d+1 收盘比会把"隔夜行情把触发价甩到另一侧"**误报**成"梯子埋反了"（实测 8 条 → 修正后 **3 条真实**）。另一类真发现：「**开盘即已满足**」的跌破档（跌破价设在研究日收盘**之上**）= 实质市价了结，不是价格档，梯子语义上的"分批"会变成开盘一次性成交 |
| 4 | **风控纪律** | `risk_*` 配置**是否真被遵守 / 触发过** | ⚠️ **限值三项全空时返回 `—`（无从评估），不能算满分**——那是"没违规"的假绿灯。三个限值在 `_SETTING_FIELDS` 里、冻进 `config_json`、由 `trust.py` 消费（`single_cap`/`cap = ... or 0`/止损）；**为 `None` 时不加任何约束**。⚠️（2026-09-12 加）**首日的持仓类违例不计分**：首日没有可执行计划（§2.6），团队那天无从动手，扣分等于用起跑线的位置判失职——实测 run 4 的三条违例**全部**落在首日（两条超配 + 一条由复权口径造成的假浮亏），把"风控 40 分"读成了团队失职。现在它们进 `inherited_violations`，照「梯子合理性」里"首日没有研究日，跳过"的同一先例处理 |
| 5 | **前后一致** | 连续两天的决策**是否无理由反手** | ⚠️ **同日买卖档不是"反手"**：梯子天然双面（`build_ladders` 的 exit/entry/hold 三组），逐条扫会把同一天的 买→卖 当成反手（实测 35 条假阳性）。改成比**净倾向**（`Σ建仓档权重 − Σ减仓档权重`）的**符号**跨日翻转 |
| 6 | **现金纪律** | 默认"现金为头寸"的倾向**与行情是否矛盾** —— 专门看它是不是"**永远不敢下手**" | `cash_target` 序列 + 实际现金比例 + 动作构成；`always_high` / `no_deploy` 两类扣分。★ 另加**同日对照**：`cash_target < 70%`（宣布要大幅建仓）且**确实给了进场档**，而**当日**实际现金仍 ≥ 90% —— 宣布的目标仓位**靠自己的档位够不着**。实测 run 2 命中 1 天（09-11 宣布投 32%，进场档合计权重仅 24%，实际现金仍 95%）。⚠️ **必须同日比**：step 的 `plan_json` 是"**在 d 日执行的那份**计划"，要和 d 日本身的现金比，拿 d+1 比会整体错开一天。**扣分刻意温和**（10/天封顶 30）："够不着"与"有纪律地不追"这条判据分不清，把存疑当失误打分会给出一个看起来精确、其实没有依据的数 |

> ⚠️ **写这套判据时踩到的最大一个坑**：**落库的 `plan_json` 动作里没有 `kind` 字段**。
> 它只有 `action` / `code` / `name` / `reason` / `target_weight` / `trigger_price` /
> `trigger_type` / `volume_ratio_min` —— 而 `kind`（`exit`/`entry`/`hold`）是**监控接口由
> `build_ladders` 现算**出来的。所以判方向**只能**用 `action in ENTER/EXIT`；写成
> `a.get("kind") == "entry"` 会**永远得到 `None`**，判据**静默失效**（不报错、只是恒不命中，
> 表现为"这一项永远是满分"）。同一份代码里「前后一致」一直用的是 `action`，那才是对的——
> **一个文件里两种写法并存时，抄错的那一处不会报错，只会让一条判据变成摆设。**
> 另有一个同形状的误报：把"抽象理由"判据用到 `hold` 动作上，会把**"维持 0% 仓"**这类
> 理由（引用的是**数据闸门**："跟踪指数/IOPV/规模未核实"）判成"凭感觉下注"——
> 实测 4 条**全是**这类误报。`hold` 不应该被要求引价位。
